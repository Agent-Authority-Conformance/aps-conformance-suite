# Contributing to aps-conformance-suite

This repo publishes the conformance fixtures for the Agent Passport System: deterministic vectors, schemas, and independent verifiers that let anyone check an implementation against the protocol from the bytes up, with no trust in us or in each other. That property only holds if the suite itself stays deterministic, recomputable, and precisely scoped, so contributions here run under a tighter policy than a typical fixture repo.

## The fastest way to contribute: run it and report

The most valuable contribution is a recompute or breakage report. Clone cold, run `npm ci --include=dev && npm test`, or recompute the fixtures with your own implementation, and file a run report with the verbatim output (docs/RUN-REPORT.md explains both run modes and the issue form). Reports of vectors that fail where they should pass, pass where they should fail, or diverge between the two verifiers get priority attention. No PR needed.

## What lands by PR

**Corrections to existing vectors and docs.** Wrong bytes, broken determinism, doc errors: open a PR with the failing recompute shown verbatim in the body. These merge quickly once we reproduce the failure.

**New vectors inside existing failure classes.** Open an issue first describing the case and which existing class and schema it exercises. A vector PR will be merged when:

1. **It is deterministic and recomputable.** Seeds recorded, canonical bytes produced under RFC 8785 JCS, and every check reproducible from the bytes up by both verifiers with no network access.
2. **It stays inside the existing schema and taxonomy.** No new fields, no new failure classes, no new verifier behavior. If your case needs any of those, it belongs in the section below, not in a vector PR.
3. **Generation is included.** The script or exact procedure that produced the vector ships with it, so the vector can be regenerated, not just replayed.
4. **Scope is one concern.** Fixture additions do not bundle schema edits, README changes, or verifier changes. Mixed PRs will be asked to split.

**Admission of external-system vector families.** Rule clarification, 2026-08-28: the former wording described verification as an end-to-end property of an external family. Existing run records were instead produced and attributed at distinct layers. The rule below makes that provenance explicit.

External-system vector families (fixtures generated by another implementation) are admitted by layer and remain labeled as ingestions from their source system. Independently recomputable claims originating in the external system, including bytes, digests, and signatures, land only with a record produced by a runner who authored neither the family nor the implementation used to recompute that claim. The family README enumerates those claims separately so that no imported claim can be folded into a wrapper or integration layer.

Other layers may land with an author-produced record. Each such record names its runner, mode, implementation, and the authorship relationship that prevents it from being labeled independent. Every layer merged without an independent record is listed in `docs/OPEN-RUNS.md`. A later independent run is appended as a new record and removes that layer from `docs/OPEN-RUNS.md` in the same commit; it does not alter or replace the earlier record.

Records append and are never removed. A merged family is a set of attributed run records and asserts nothing beyond them; merge is not an end-to-end verification or a family-level verdict. These requirements state the minimum record for admission, not an obligation to admit. Ask in an issue before building. `npm test` is the core APS corpus run and does not execute external families; each carries its own documented reproduction command, and its runs are recorded with attribution in its `SOURCE.md` or under `interop/`.

Every external family carries a section titled **Verification split** in its README (or its `SOURCE.md` where that is the family document). One entry is recorded for each distinct verification claim: `layer / claim; runner; Mode A | Mode B; author-produced | independent; implementation`. Every author-produced entry also states the authorship relationship that prevents the record from being classified as independent. The section closes with: "These records are attributed per layer. Merge of this family is not an end-to-end verification or a family-level verdict." The only labels are `Mode A` / `Mode B` (how the check was performed, per `docs/RUN-REPORT.md`) and `author-produced` / `independent` (who performed it relative to the vectors and the implementation); explanatory prose such as "maintainer-reproduced" never stands in for a label.

## What does not land by PR

Failure-class names, record fields, layer boundaries, verifier semantics, and normative README text are conformance vocabulary. Names published here are names downstream implementations bind to, so they are decided by the maintainer, as schema owner, on the maintainer's timeline. Proposals are welcome as issues and are genuinely read; a PR is not the vehicle for them, and a proposal that returns may return under different naming, placement, or none at all. PR quality does not change this: a technically perfect PR that mints vocabulary will be closed with thanks, not merged.

## What merging means

A merge means the vectors verified as deterministic, in scope, and correctly labeled. It is not an endorsement of the contributing system, and it implies nothing about that system's status, adoption, or production use. Please do not describe a merged fixture as APS validating, adopting, or partnering with anything.

## Mechanics

Fork, branch from `main`, PR against `main`. Both verifiers must pass locally before you open the PR; paste the verbatim output in the PR body. License is Apache 2.0 and contributions are accepted under the same terms.
