# C19: fail-closed handling of unrecognized revocation resolutions

This fixture exercises one narrow forward-compatibility property at the
`AuthorityDelegationV1` revocation-resolver boundary.

The current TypeScript and Python APS SDKs recognize only the exact revocation
answers `active` and `revoked` as determinate outcomes. Other resolver answers,
or a resolver exception, are normalized to an unknown revocation result and
chain verification returns:

    state = indeterminate
    failure code = REVOCATION_UNKNOWN

The candidate string `suspended` is included because suspension is being
considered for a future APS revision. This fixture does not define suspension.

## Why this fixture exists

draft-pidlisnyi-aps-03 says that an unavailable or stale revocation result is
indeterminate. It does not currently state a general forward-compatibility rule
for a future resolver outcome that a draft-03 implementation does not
recognize.

The reference TypeScript and Python SDKs currently fail closed at this
boundary. C19 makes that behavior executable and reviewable instead of
inferring it from one implementation.

The active control also proves that the minted chain, key resolution, trust
decision, signatures, time window, attenuation and linkage are valid before
the synthetic revocation result is introduced.

The revoked control proves that an understood terminal revocation still
produces `invalid / REVOKED`, rather than being collapsed into the unknown
case.

## Cases

There are 14 cases:

1. `active` control
2. `revoked` control
3. future value `suspended`
4. casing variant `SUSPENDED`
5. whitespace variant ` suspended `
6. `null`
7. number `0`
8. number `1`
9. boolean `false`
10. boolean `true`
11. object `{}`
12. array `[]`
13. resolver exception
14. only the root returns `suspended`, and the child returns `active`

Every case except the two controls must return exactly:

    indeterminate
    REVOCATION_UNKNOWN

at chain index `0`.

The root-only case additionally checks that a known-active child cannot make a
chain valid when the root's revocation status is not understood.

## chain.json

`chain.json` holds one root `AuthorityDelegationV1` and one child, both valid
at the fixture's `now` when the revocation resolver answers `active`. It is
generated by `mint.py` from published seed labels, so it carries no secret
material and regenerates byte for byte:

    python3 fixtures/revocation-resolution-forward-compat/mint.py

After regeneration `git diff` on `chain.json` should be empty. The active
control case checks that the chain really is valid before any synthetic
revocation answer is introduced.

## TypeScript

The repository root currently pins the published `agent-passport-system`
package.

From the conformance-suite root:

    npm ci --include=dev
    npm run verify:revocation-resolution-forward-compat

It also runs as the last step of `npm test`.

Expected final line:

    C19 TypeScript: 14/14 passed

The TypeScript runner intentionally crosses the published compile-time
`RevocationResolution` type for the malformed/future cases. That is the point
of the fixture: it tests the runtime boundary when an integration, transport
adapter, future producer or untyped caller supplies a value outside the
current `active | revoked | unknown` union.

## Python

Run against the actual Python SDK under test, for example:

    PYTHONPATH=/path/to/agent-passport-python/src \
      python3 fixtures/revocation-resolution-forward-compat/validate.py

Expected final line:

    C19 Python: 14/14 passed

The current Python verifier requires the resolver answer to be an exact `str`
whose value is exactly `active` or `revoked`, and everything else is treated as
unknown.

## What a pass establishes

For the exact SDK revision that was run, a pass establishes that:

- exact `active` can produce a valid chain
- exact `revoked` produces `invalid / REVOKED`
- the tested unrecognized or unusable resolver outputs do not become active
- an exception from the revocation resolver does not become active
- an unrecognized root result makes the chain indeterminate even when the
  child resolves active
- the failure is surfaced as `REVOCATION_UNKNOWN`

## What a pass does not establish

A pass does **not** establish that:

- draft-pidlisnyi-aps-03 normatively requires all unrecognized future
  revocation values to map to indeterminate
- every independent draft-03 implementation already behaves this way
- `suspended` is the selected draft-04 wire value
- suspension semantics, lock records, release or override semantics are
  correct
- an older implementation will receive a future suspension value in this
  exact representation
- the child-issuance path has the same forward-compatibility behavior
- a suspension record itself is authorized, signed or valid
- any physical system reached a stopped or safe state

This fixture is therefore evidence about one verifier boundary, not a
conformance verdict about suspension as a protocol feature.

## Protocol use

If APS later requires the property generically, the protocol text still needs
a normative rule such as:

    A verifier that receives a revocation-resolution outcome it does not
    recognize MUST NOT treat that outcome as active. Unless another
    specification defines a stronger result, it MUST treat the revocation
    state as not established.

The exact wording and wire representation remain design questions. This
fixture should not decide them by accident.
