# aeoess receipt vectors (bilateral exchange, reciprocal leg)

Source: generated by aeoess from the shipped `aps-receipt-v1` construction in
`agent-passport-system/src/v2/receipt-core/receipt.ts`, schema
`aeoess-aps-receipt-vectors-v1`. Round 1 authored 2026-08-05.

This is the return leg of `../receipts-amdal/`. There AgentLair mints signed receipts and
we verify them. Here we mint and they verify. The vector classes are deliberately mirrored
so a result on one side is comparable to the same-named result on the other, and the three
places where the two profiles genuinely differ are called out below rather than smoothed
over.

       = 987789ff25a0c63c4224226aace869b6620ef1af74bec35fad6f3e25297beda8

       did:key:z6MkuJUMZwUEso3NatcaRiwghQbQJAMv7Gfn5GNpVjeYMN51

**Both are burned test keys.** The private halves are published above on purpose and have
no value beyond regenerating this fixture. Neither is a production APS signer, neither
appears in any other aeoess corpus, and neither should ever be accepted as authority for
anything. This mirrors the convention already used by
`runners/generate_synthetic_regression.py`, which publishes its seed for the same reason.

Both key ids belong to the same issuer DID. `#k1` carries key A material and signed every
valid vector. `#k2` carries key B material, resolves successfully, and never signed
anything. That is what makes the wrong-signer vector a real "resolution succeeds,
verification fails" case rather than an unresolvable key.

## Scope

Transport and identity only: RFC 8785 JCS canonicalization, domain-separated `receipt_id`
recomputation, domain-separated Ed25519 receipt signatures, and closed-schema validation.
It asserts nothing about APS receipt semantics, nothing about whether any described action
occurred, and nothing about any production issuer's runtime behaviour. A run records what
was executed against which bytes at which time. It is not a conformance verdict.

## Profile, as implemented by the shipped code

Read out of `src/v2/receipt-core/receipt.ts` and `src/v2/receipt-core/jcs.ts` at
`agent-passport-system` commit `80705d4`, not paraphrased from a spec.

- Canonicalization: RFC 8785 JCS, keys sorted at serialization time by UTF-16 code unit, no
  whitespace, lone surrogates rejected rather than escaped.
- Scalars: string-only in this round, so JCS number canonicalization is out of scope for
  round 1, same as the AgentLair v1 set.
- `receipt_id` = `lowercase-hex(SHA-256(ASCII("APS-RECEIPT-ID-V1") || 0x00 ||
  UTF8(JCS(receipt without receipt_id and signatures))))`.
- Signature `value` = `lowercase-hex(Ed25519-Sign(key, ASCII("APS-RECEIPT-SIG-V1") || 0x00 ||
  UTF8(JCS(signature_form))))` where
  `signature_form = {"receipt": receipt without signatures, "signer": {signer, key_id, alg}}`.
  The signature form **includes** `receipt_id`, so the signature binds the content-addressed
  body and the signer's own identifier and algorithm.
- Key resolution: an explicit `(signer, key_id)` table, published inline in the fixture.
  `receipt-core` takes a `resolveKey` callback returning raw 32-byte lowercase-hex, so there
  is no did:key derivation inside the verifier. The did:key encoding of each key is
  published alongside the hex so an existing did:key resolver can confirm it derives the
  identical bytes.
- Evaluation order: schema, then `receipt_id`, then key resolution, then signature.

## Three places the two profiles differ

These are the interesting part of the exchange and are stated plainly rather than hidden in
a passing test.

**1. Evaluation order is reversed.** AgentLair evaluates the signature before `receipt_id`,
so a tampered id can never be masked by a bad signature. We recompute `receipt_id` before
the signature, per `draft-pidlisnyi-aps-03` section 5.2 ("A verifier MUST recompute
receipt_id before signature verification"). Neither order is wrong; they defend different
things.

**2. We do not short-circuit, and our result is a list.** AgentLair returns a single code
plus a stage. `verifyReceiptV1` runs every applicable check and returns
`{valid, receipt_id_valid, signature_results, errors}`. A content mutation after signing
therefore reports **two** errors on our side and **one** on theirs, because `receipt_id`
covers every member except `receipt_id` and `signatures`. The `sig-invalid` vector is
published with both codes for exactly this reason. A runner that expects one code per
negative will need to widen before it can consume this set.

**3. The result shape is still two-valued.** `verifyReceiptV1` returns a boolean plus an
error list. It does **not** return the four-value valid / invalid / indeterminate /
unsupported result that `draft-pidlisnyi-aps-03` section 3.3 requires, and that AgentLair
was told in writing on 2026-07-29 to expect. That gap has not closed. It is recorded in the
fixture's `profile.result_shape` so nobody has to discover it by running the set.

## delegation_chain_root

`delegation_chain_root` is **not a member of the `aps-receipt-v1` envelope**. The envelope
is a closed schema; adding the field to a receipt makes our own verifier return
`ReceiptV1: unknown field delegation_chain_root`. It lives instead on the v1 `PolicyReceipt`
(`src/core/policy.ts`) and on the v2 accountability and instruction-provenance records.

The `chain-root` vector therefore carries the worked example beside an ordinary valid
receipt rather than inside it: `delegation_chain` is the input array and
`delegation_chain_root` is the expected digest. The construction is

```
delegation_chain_root = lowercase-hex(SHA-256(UTF8(JCS(chain))))
```

over the chain array alone. **No domain tag and no 0x00 separator byte**, which is the
opposite of `receipt_id`. That asymmetry is deliberate and is being published rather than
quietly fixed: the value is already emitted by shipped code, so changing the preimage would
silently invalidate every previously computed root. Any future correction will arrive as an
explicitly versioned construction under a new name, never as a substitution under this one.

## Integrity convention

`receipt_len` and `receipt_sha256` are flat on every vector, over utf8 of the **compact JSON
serialization in the member order as published**, not over the canonical form. Field names
match what we asked AgentLair to adopt on the token side.

One consequence worth knowing before comparing digests: `aps-receipt-2026-08-05-key-order-reversed`
has a different `receipt_sha256` from `aps-receipt-2026-08-05-valid` while sharing its
canonical bytes and its signature byte for byte. That is the property the vector exists to
demonstrate.

## Result, 2026-08-05

Two gates, deliberately not sharing a code path.

Gate A, the shipped `verifyReceiptV1` from the SDK that emitted the vectors: 6/6 match
expectation, 0 failures. This proves internal consistency and nothing more.

Gate B, `runners/aeoess_receipt_runner.py`, written fresh against the profile text with no
import from the SDK: 6/6 match expectation, 0 integrity failures, 0 chain-root failures.
Gate B independently recomputes both domain-separated preimages, the bare chain root, and
every `receipt_len` and `receipt_sha256` from the published bytes. A positive that passed
only because both sides shared one implementation would not survive Gate B.
